=============================================================================== 1.
PRODUCT VISION
===============================================================================

AgentFlow accepts a natural-language request and coordinates a team of
specialized AI agents to complete it.

The Main Orchestrator: - Understands the user’s request and extracts
requirements and constraints. - Creates a structured execution plan. -
Decomposes the plan into small, verifiable tasks. - Builds a directed
acyclic graph (DAG) of task dependencies. - Selects preconfigured
specialist agents based on skills, permissions, availability and
limits. - Dispatches independent tasks concurrently and respects
dependencies. - Collects structured agent submissions and artifacts. -
Independently verifies submissions against acceptance criteria. -
Decides whether to accept, request rework, reassign, replan or
escalate. - Pauses for human clarification or approval when policy
requires it. - Produces a final report containing the plan, task
history, agents, artifacts, verification, issues, retries, token usage,
costs and execution timing.

The platform supports both: A. Software-oriented work: coding,
debugging, testing, architecture and DevOps. B. General work: research,
writing, analysis, summarization and structured information tasks.

The Main Orchestrator is the workflow manager, not an all-purpose
worker. Specialized agents perform assigned work. The workflow engine
and database enforce state and policy. LLM output must never be treated
as authoritative state without validation.

Core product principles: - Explicit task contracts. - Controlled tool
access. - Deterministic workflow state transitions. - Independent
verification. - Bounded retries and spending. - Human approval for
sensitive or ambiguous actions. - Complete execution history. - Accurate
separation of measured cost from estimated cost. - Provider-independent
model integration. - Secure defaults and local-first development.

===============================================================================
2. FINAL PRODUCT DECISIONS
===============================================================================

Task scope: Universal (software development and general-purpose tasks).
Agent creation: Hybrid. - Preconfigured agents are available by
default. - The Main Orchestrator may propose a new specialist when a
capability is missing. - Dynamic agent proposals require administrator
approval before activation. - Agents cannot grant themselves permissions
or create privileged tools. Autonomy: Approval-based. - Agents can
perform permitted low-risk tasks autonomously. - Sensitive, external,
destructive or irreversible actions require human approval. - Repeated
failures and unresolved ambiguity are escalated. Implementation: MVP
first, then production-grade evolution. Deployment: Local development
first; architecture remains cloud-ready. Architecture: Modular monolith
with separate API and worker processes. Repository: One Git repository.
Initial agents: Research, Analyst, Developer, Writer, QA and General.

MVP exclusions: - Kubernetes and microservice deployment. - Public agent
marketplace. - Autonomous privilege escalation. - Unrestricted shell
execution. - Production deployment performed by agents. - Multi-region
deployment. - Self-training or self-modifying agents. - Complex billing
and subscription management. - Advanced organization-wide enterprise
administration.

Do not implement excluded capabilities unless the owner explicitly
changes scope.

3. TECHNOLOGY BASELINE
===============================================================================

Frontend: - Next.js App Router. - TypeScript with strict mode. -
React. - npm (do not assume pnpm is installed). - Vitest for
unit/component tests. - Playwright for end-to-end tests. - Use an
accessible, consistent component system. Avoid unnecessary UI libraries.

Backend: - Python 3.12 as the initial compatibility baseline. -
FastAPI. - Pydantic v2 and Pydantic Settings. - SQLAlchemy 2.x. -
psycopg 3 synchronous PostgreSQL driver for the initial
implementation. - Alembic for schema migrations. - Pytest and HTTPX for
tests. - Ruff for linting and formatting. - mypy or Pyright only where
configured consistently; do not add redundant type tools.

AI and orchestration (later phases, not Phase 1): - LangGraph for
stateful orchestration and conditional routing. - LiteLLM as a
provider/model gateway. - Structured outputs validated with Pydantic. -
Model provider and model name configured via environment variables. -
Mock model adapters for deterministic automated tests.

Background execution: - Redis. - Celery workers. - PostgreSQL is the
authoritative business-state store. - Redis is transport/cache, not the
permanent source of workflow truth. - Use transactional outbox or an
equivalent reliable dispatch mechanism when task dispatch is introduced,
so database commits and queue publication cannot silently diverge.

Storage: - Local filesystem for MVP artifacts, outside source-controlled
code. - PostgreSQL stores artifact metadata, checksum, ownership and
relative storage key. - Design an interface that can later support
S3-compatible object storage without implementing cloud storage in the
MVP.

Local infrastructure: - Docker Compose for PostgreSQL and Redis when
Docker is available. - Bind infrastructure ports to 127.0.0.1 only. -
Named volumes for local persistence. - Health checks for dependencies.

Observability: - Structured logs with request_id, workflow_id, task_id
and execution_id where applicable. - Persist workflow events. - Add
OpenTelemetry and advanced dashboards in a later phase, not as a Phase 1
blocker.

CI: - GitHub Actions. - Separate backend and frontend checks. -
Formatting, linting, tests, type checks and build validation. - Do not
add cloud deployment workflows for the MVP.

Versioning: - Pin dependency versions using lock files where
supported. - Avoid floating dependency versions in reproducible
environments. - Document the exact runtime versions in README.

Compatibility note: The developer uses Windows 11 and PowerShell. Verify
installed tools before choosing commands. Do not assume Docker, pnpm, uv
or a particular Python version is installed. If Docker is absent, report
that clearly and offer a local PostgreSQL/Redis alternative or ask the
developer to install Docker Desktop. Do not silently skip infrastructure
verification.

4. HIGH-LEVEL ARCHITECTURE
===============================================================================

Logical flow:

USER | v NEXT.JS FRONTEND | v FASTAPI APPLICATION | +–> Authentication
and workspace authorization +–> Workflow API +–> Task manager +–> Agent
registry +–> Approval manager +–> Usage and cost service | v
ORCHESTRATION LAYER (LangGraph in later phase) | +–> Prompt
understanding / planner +–> DAG validation +–> Agent selector +–>
Scheduler +–> Supervisor / verifier +–> Recovery manager +–> Final
report generator | v REDIS + CELERY | +–> Research agent worker +–>
Analyst agent worker +–> Developer agent worker +–> Writer agent worker
+–> QA agent worker +–> General agent worker | v RESULT SUBMISSION | v
VERIFICATION | +–> PASS: accept task +–> REWORK: return corrective task
+–> REASSIGN: select another authorized agent +–> REPLAN: revise
remaining DAG under policy +–> HUMAN: pause for approval or
clarification +–> FAIL: terminal failure with diagnostics | v FINAL
REPORT AND ARTIFACTS

Persistence: - PostgreSQL stores users, workspaces, agents, versions,
workflows, tasks, dependencies, executions, artifacts metadata,
verification results, approvals, usage and events. - Redis transports
background jobs. Do not use Redis as the sole record of task state. -
Local artifact directory stores actual files; database stores metadata
and checksums.

Deployment shape: - One backend codebase. - API process and Celery
worker process run separately. - One frontend process. - PostgreSQL and
Redis are local infrastructure dependencies. - Do not split into
microservices for MVP.

Architecture ownership: - API routes validate HTTP requests and call
application services. - Application services own business rules and
transactions. - Repositories own persistence queries. - Orchestration
nodes decide workflow next steps but must use services for state
mutations. - State transition service validates every status change. -
Agent runtime executes one task contract and returns a structured
submission. - Verification service accepts or rejects a submission based
on explicit criteria. - Usage service records provider-reported usage
and pricing snapshots. - Reporting service composes persisted facts; it
must not invent metrics.

===============================================================================
5. LOW-LEVEL DOMAIN DESIGN
===============================================================================

5.1 Workflow

A workflow represents one user request and its overall execution.

Required attributes: - id (UUID) - workspace_id - created_by_user_id -
prompt - normalized_requirements (JSON) - status - autonomy_policy -
budget_limit - currency - max_parallel_tasks - deadline (nullable) -
created_at, updated_at, started_at, completed_at

5.2 Workflow task

A task is one independently assignable unit of work.

Required attributes: - id (UUID) - workflow_id - parent_task_id
(nullable) - title - description - required_skills (JSON or normalized
representation) - input_references - expected_output_schema -
acceptance_criteria - priority - status - assigned_agent_id (nullable) -
attempt_count - created_at, updated_at, started_at, completed_at

5.3 Task contract

Every dispatched task must have: - Objective. - Context and input
references. - Required skills. - Expected deliverables. - Output
schema. - Acceptance criteria. - Dependencies. - Allowed tools. -
Execution timeout. - Token/cost budget if available. - Retry policy. -
Security classification.

Agents must not mark tasks COMPLETED. They submit results. The
platform’s verification service and authorized workflow service control
acceptance.

5.4 Agent definition

Each agent definition contains: - Agent ID. - Display name and
description. - Category. - Skills/capabilities. - System instruction
reference/version. - Model provider and model configuration. - Tool
permission manifest. - Input/output schema versions. - Timeout and
resource limits. - Enabled/disabled status. - Agent version. - Whether
it is built-in or workspace-created. - Creator and approval metadata.

Never store provider API secrets in an agent definition. Store secret
references or use environment-based configuration.

5.5 Agent execution

An execution represents one attempt by one agent on one task. Record: -
Task and agent IDs. - Agent version. - Attempt number. - Execution
status. - Started and completed timestamps. - Error classification and
safe diagnostic details. - Output summary. - Artifact references. -
Model usage references. - Trace/correlation identifiers.

5.6 Verification

Verification is separate from agent execution. Record: - Task ID and
execution ID. - Deterministic checks performed. - Semantic evaluation
result if used. - Pass/fail decision. - Issues with severity and
evidence. - Verifier identity/version. - Timestamp. - Rework
instructions.

5.7 Human intervention

Intervention types: - CLARIFICATION. - APPROVAL. - REJECTION. -
MANUAL_RECOVERY.

Store requester, target workflow/task, requested action, context,
status, expiry, responder, response and timestamps. Approval decisions
must be attributable to an authenticated user.

5.8 Workflow events

Append an event for every important transition: - WORKFLOW_CREATED. -
PLAN_CREATED. - TASK_CREATED. - TASK_ASSIGNED. - TASK_QUEUED. -
TASK_STARTED. - AGENT_SUBMITTED. - VERIFICATION_STARTED. -
VERIFICATION_PASSED. - VERIFICATION_FAILED. - RETRY_REQUESTED. -
TASK_REASSIGNED. - APPROVAL_REQUESTED. - APPROVAL_RESOLVED. -
TASK_COMPLETED. - WORKFLOW_COMPLETED. - WORKFLOW_FAILED. -
WORKFLOW_CANCELLED.

Events should be append-only through application permissions. Never
update old event records to rewrite history. Do not store secrets or
sensitive raw prompts in logs/events unless explicitly required and
protected.

===============================================================================
6. TASK STATES AND TRANSITIONS
===============================================================================

Initial state set: PENDING READY ASSIGNED QUEUED IN_PROGRESS SUBMITTED
VERIFYING REWORK_REQUIRED WAITING_APPROVAL BLOCKED ESCALATED COMPLETED
FAILED CANCELLED

Rules: - PENDING: task created, dependencies may be unresolved. - READY:
all dependencies accepted and task is eligible for assignment. -
ASSIGNED: authorized agent selected. - QUEUED: dispatch accepted by the
queue/outbox mechanism. - IN_PROGRESS: worker has claimed execution. -
SUBMITTED: agent has returned a structured result. - VERIFYING:
independent checks are running. - REWORK_REQUIRED: verification failed
but recovery is permitted. - WAITING_APPROVAL: user action is
required. - BLOCKED: required dependency or external condition is
unresolved. - ESCALATED: recovery policy requires human attention. -
COMPLETED: platform accepted the deliverable. - FAILED: terminal failure
after allowed recovery. - CANCELLED: user or authorized operator
cancelled the work.

Rules: - Validate transitions centrally; do not let arbitrary code
mutate status. - Use transactions and concurrency controls for task
claiming and transitions. - A task cannot depend on itself. - Reject
cycles in a workflow DAG. - A task cannot become READY until all
required dependencies are COMPLETED. - A workflow cannot become
COMPLETED while required tasks are unresolved. - Retries create new
execution attempts; preserve previous attempts and results. - A failed
verification does not erase the original agent submission. -
Cancellation must be cooperative and persisted. - Duplicate queue
delivery must not create duplicate accepted side effects. - Use
idempotency keys for externally initiated operations.

Recovery defaults (configurable): - Maximum attempts per task: 3 total
attempts. - Maximum reassignment: 1. - Default agent timeout: 600
seconds. - Default maximum parallel tasks: 3. - Retry transient
infrastructure failures with bounded backoff. - Do not blindly retry
deterministic validation failures; attach corrective instructions. -
Escalate after retry/reassignment policy is exhausted. - Budget
exhaustion pauses or terminates according to workflow policy. - Never
loop indefinitely.

DAG rules: - Validate acyclicity before execution. - Schedule only READY
tasks. - Execute independent tasks concurrently up to configured
limits. - Persist dependency relationships. - Recompute readiness after
dependency completion. - Replanning must preserve completed task history
and require validation of the revised DAG.

===============================================================================
7. AGENT MODEL AND INITIAL SPECIALISTS
===============================================================================

All agents implement one common interface and return structured,
schema-validated submissions.

Conceptual interface:

    class BaseAgent(ABC):
        async def execute(self, task_contract, context) -> AgentSubmission:
            ...
        def get_capabilities(self) -> AgentCapabilities:
            ...
        def validate_output(self, result) -> ValidationResult:
            ...

Initial agents:

1.  Research Agent Skills: research, source extraction, comparison,
    evidence summaries. Tools: only approved search/retrieval tools when
    configured. Output: findings, source references, caveats and
    artifacts.

2.  Analyst Agent Skills: structured analysis, calculations, data
    interpretation. Tools: restricted Python analysis tools only when
    enabled. Output: analysis, assumptions, calculations and supporting
    artifacts.

3.  Developer Agent Skills: code generation, debugging, implementation.
    Tools: controlled workspace and isolated test runner only when
    enabled. Output: changed-file list, summary, tests and artifacts. Do
    not grant unrestricted host shell or production access.

4.  Writer Agent Skills: reports, documentation, editing and structured
    writing. Tools: artifact writer. Output: document and content
    summary.

5.  QA Agent Skills: test design, test execution, acceptance validation.
    Tools: approved test runner. Output: test results, failures and
    evidence.

6.  General Agent Skills: general task completion and coordination
    support. Tools: minimal common tools. Must not bypass specialist
    permissions or the orchestrator.

Agent selection should consider: - Required skill match. - Tool
availability and permission compatibility. - Agent enabled status. -
Current workload. - Historical quality metrics when enough evidence
exists. - Model suitability, latency and cost. - User/workspace policy.

Do not implement a complex machine-learning ranking model for the MVP.
Start with explainable rule-based scoring and persist the selection
rationale.

Dynamic agent creation: - The planner may emit an AgentProposal. -
Validate proposal schema and required capabilities. - Review requested
tools and permissions. - Reject privilege escalation or unsupported tool
requests. - Require administrator approval. - Register a new immutable
agent version after approval. - Never execute arbitrary code supplied in
an agent proposal. - Agent proposals are not automatically active.

===============================================================================
8. VERIFICATION AND RECOVERY
===============================================================================

Verification has two layers.

Layer A: deterministic checks - Pydantic schema validation. - Required
fields and artifact presence. - File existence and checksums. -
Unit/integration test results. - API contract checks. -
Permission/policy checks. - Required evidence checks.

Layer B: semantic evaluation - Does the submission satisfy the
objective? - Does it meet every acceptance criterion? - Is it complete
and internally consistent? - Are assumptions and limitations explicit? -
Is supporting evidence provided? - Does the result conflict with
requirements?

An LLM evaluator may assist semantic evaluation but must return
structured findings with criterion IDs, evidence and reasons. It is not
a substitute for deterministic tests.

Verification outcomes: - PASS: accept task. - REWORK: create corrective
instructions and bounded new attempt. - REASSIGN: choose another
suitable authorized agent. - REPLAN: revise remaining workflow tasks
after DAG validation. - HUMAN: pause for clarification/approval. - FAIL:
terminal failure with a diagnostic report.

Never claim a software artifact is correct merely because an LLM says it
is. Execute tests and inspect actual outputs where possible.

===============================================================================
9. HUMAN-IN-THE-LOOP POLICY
===============================================================================

Human intervention is a first-class workflow feature.

Require approval for: - Destructive or irreversible actions. -
Production deployment or production infrastructure changes. - Database
migrations against non-local environments. - External communications or
purchases. - Access to sensitive data. - New or expanded permissions. -
Activation of dynamically proposed agents. - Actions exceeding
configured budget or risk thresholds.

Ask for clarification when: - Requirements are materially ambiguous. -
Required inputs are missing. - Multiple interpretations lead to
different outcomes. - The workflow cannot proceed safely.

Escalate when: - Bounded retries fail. - No suitable authorized agent is
available. - Required tools are unavailable. - Budget/time limits
prevent completion. - Verification cannot establish correctness.

The approval request must show: - What action is proposed. - Why it is
needed. - Which agent requested it. - Risks and potential
consequences. - Relevant evidence and artifacts. - What happens if
approved or rejected.

A user approval must be authenticated, authorized, recorded and bound to
the specific action. Do not treat a generic approval as permission for
unrelated future actions.

12. TOKEN USAGE AND COST ACCOUNTING
===============================================================================

All LLM calls must eventually pass through a centralized model gateway.
Do not let each agent implement separate untracked provider clients.

Record per call: - workflow_id - task_id - execution_id - provider -
exact model identifier - input tokens - output tokens - cached input
tokens when reported - provider-specific usage fields -
input/output/total cost - currency - pricing version or snapshot -
provider request ID if available - timestamp

Use provider-reported usage as the source for token counts whenever
available. Do not estimate token counts and label them actual.

Illustrative text-model formula:

cost = (billable_input_tokens * input_price_per_million +
billable_output_tokens * output_price_per_million) / 1,000,000

Handle cached tokens, image/audio usage, batch discounts and
provider-specific billing rules separately. Snapshot the applicable
pricing data so historical cost reports remain reproducible.

Separate: - LLM costs. - External tool/API costs. - Storage costs. -
Infrastructure costs. - Estimated/unallocated costs.

For local MVP, infrastructure cost may be shown as not measured or
estimated. Never present an estimate as an actual provider charge.

Track failed calls and retries too. Do not double count provider retries
if the provider’s response already represents a single billed request.

13. SECURITY REQUIREMENTS
===============================================================================

Authentication: - Use Argon2id password hashing. - Use short-lived
access tokens. - Implement refresh token rotation if refresh tokens are
used. - Store refresh tokens securely as hashes or equivalent protected
representations. - Do not log credentials or tokens. - Enforce
authorization on every resource endpoint.

Authorization: - Roles: Owner, Admin, Member, Viewer. - Every workflow,
task, artifact, agent and approval is workspace-scoped. - A user must
not access another workspace by guessing UUIDs. - Approval permission is
distinct from workflow execution permission. - Enforce authorization in
backend services, not only frontend visibility.

Secrets: - Keep secrets in environment variables or a secret manager. -
Commit only .env.example with placeholders. - Never return secrets from
APIs. - Never put provider API keys in agent prompts or model-visible
tool results. - Redact secrets from logs and exception messages.

Agent/tool security: - Explicit per-agent tool permission manifest. -
Enforce permissions in a server-side tool gateway. - Treat user input,
retrieved documents, web pages, tool output and agent output as
untrusted. - Protect against prompt injection and path traversal. -
Validate file type, size and storage path. - No unrestricted host shell
execution. - No production database credentials available to agents. -
No network access by default for code execution. - Require approval for
sensitive external actions. - Do not rely on prompt instructions as a
security boundary.

Code execution: - If/when implemented, use isolated containers with
non-root user, resource limits, restricted filesystem, restricted
networking and timeouts. - Do not mount the developer’s home directory
or host Docker socket. - Treat container isolation as one layer, not a
complete security guarantee. - Keep execution disabled in Phase 1.

Reliability: - Bounded retries. - Idempotent task claiming. -
Transactional state changes. - Durable event history. - Timeouts. -
Dead-letter handling for failed background jobs. - Graceful shutdown. -
Health/readiness checks. - Backup/restore documentation before
cloud/production use.

instructions in CLAUDE.md as persistent project guidance. 2. Use

to multiple agents that may modify the same files. 4. Parallelize
independent read-only investigation and independent checks when useful.
5. Keep final integration, architecture consistency and verification

not the entire repository indiscriminately. 7. Use the available project
tools and test commands rather than guessing. 8. Use plan mode before
broad changes; return to normal implementation only after the plan is

Update documentation and progress state. 9. Commit only after all
required checks pass. 10. Report any unverified checks honestly.

E. Parallel work Use parallel tool calls or subagents only when tasks
are independent and file ownership is clear. Examples: - Read frontend
package configuration and backend project configuration in parallel. -

changes are complete. - Ask one subagent to review security while the

migration and code that depends on the not-yet-created schema. -
Multiple agents editing the same files. - Sequential steps with
unresolved decisions. - Git operations that depend on previous changes.
Never guess missing parameters to force parallel execution.

F. Context and long-running work - Maintain progress.md after every
completed implementation step. - Maintain IMPLEMENTATION_PLAN.md with
statuses: NOT_STARTED, IN_PROGRESS, BLOCKED, DONE. - Record decisions in
docs/ADR. - Before ending a session, leave the repository in a coherent
